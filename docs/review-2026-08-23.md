# 2026-08-23 — The conveyor belt gets a receipt

User brief: *"el tablero (grilla) no se mueve, por lo que viene de derecha a
izquierda es como una banda transportadora que se mueve solo cuando el pj
camina de la columna [1] a la [2] … si el movimiento es exitoso (se consume
una patica rosada IMPORTANTE) el mundo se deberá correr uno a la izquierda y
la verificación debería ser solo confirmar que dicho movimiento se dio."*

Two goals: (1) find and fix the origin of the bad pathfinding decisions, with
tests that keep them fixed; (2) cut the overengineering around transitions,
phantom taps and error toasts.

Evidence base: run `20260823T074036_943730Z` — 200 steps, 4:17, 45 oranges,
+3745 energy, 171 paws spent.

## FIXED

### 1. The paw ledger replaces every inference about whether a tap landed

`step_ledger.py` (new). The game charges one pink paw per step it takes, and
the HUD counter is **legible on 150 of 150 recorded frames (100%)**.

Measured on the same run, predicting the next player cell:

| oracle | accuracy |
|---|---|
| trusting the taps we sent (what the runner assumed at emit) | 133/138 = 96.4% |
| the paw receipt | **135/136 = 99.3%** |

The receipt's single "miss" is a frame where no paw was charged and vision
nonetheless resolved the player one row away — that is a vision error the
ledger *catches*, not one it makes.

The receipt cannot answer in 2 of 138 frames (1.4%), always a misread digit.
There is now one quantity — *how many of the taps did the game take* — with a
strict order of authority behind it: **receipt → pixels → assume**. No two
mechanisms arguing.

Deleted with it:
- `scroll_shortfall_wait` and its WAIT (14 frames of the run).
- `silent_rejection`, `rejection_needs_grace`, `pending_rejection` and the
  grace-frame WAIT (9 frames). `silent_rejection` admitted in its own
  docstring that it could not judge a scroll ride; the receipt has no such
  blind spot.
- The reconcile-by-shifting-memory-back-and-forth block, and both
  emit-time optimistic shift blocks (five memory stores each). Taps are now
  claims; the belt advances once, at the top of the next frame, from the
  receipt.

A refused tap is a *fact to replan from*, not a maybe to sit out — so nothing
waits for it. The same cell refused twice in a row is a wall the detector
missed and gets the phantom obstacle.

Constants settled by measurement: a steps card refunds **+5 paws**, not the
+4 this review's predecessor recorded (run frames #10 and #55: one step onto
a card, counter +4 net, player confirmed moved). See PENDING-3.

### 2. The perishable veto now checks whether the prize can be reached

Run `20260823T074036` **ended** ping-ponging (0,0)↔(0,1) until the step budget
ran out. Cause: the explorer wanted to advance; the column-0 veto forbade the
scroll on behalf of a dash orb at (3,0); row 1 was walled at columns 0 *and* 1,
so the orb was unreachable. The veto was protecting nothing at the price of
every remaining paw.

The veto now fires only for a perishable a scroll-free route still reaches,
and `allow_obstacles=False` — a 200-shard garra to rescue a 20-energy orange
is not a rescue.

It also now reads `tour_items` instead of the raw sightings, so the veto and
the plan want the same things. Previously a pickup the tour had already pruned
as not worth a detour could still hold the whole world still on its behalf.

### 3. Suspicion stopped being terrain (again), and stopped vetoing dashes

Run `20260823T074036` n=154-157: **four frames, one unchanged board, three
different answers** (down, up, down) before the dash the first of them could
already have set up. Three paws. n=80-83 is the same shape, three more paws.

Two causes, both suspicion leaking out of its lane:

- `ignored_targets` carries the loop-breaker bans *and* the suspects, and the
  explorer's `preferred` filter treated the whole set as impassable. The free
  step down happened to land on a one-frame suspect, so the bot stepped
  **backward** instead. Walking onto a maybe-item is free — it either collects
  something or nothing — so a suspect can cost a goal, never a route.
- `suspect_risk` vetoed all five dash rules whenever any unconfirmed cell sat
  in columns ≤2. Written 2026-08-21 under the old suspicion stack, where
  anything freshly seen was suspect for two frames. The world model classifies
  by *origin*: an item entering at the right edge is explained and believed on
  sight, so what stays suspect is an unexplained birth — which is what confetti
  is. Retired. Real left-band pickups are still protected: they are *believed*,
  so they sit in `orange_items`/`mid_items` and in the runner's
  `left_band_risk`, which every dash rule honours.

This closes **PENDING-4** of `review-2026-08-22.md` with the run it asked for:
`should_hold_for_suspects` ("left-band suspects are never worth waiting for")
and `suspect_risk` ("left-band suspects veto a 400-shard dash") were opposite
beliefs about the same data. The first one wins.

## New invariants in the replay harness

| invariant | what it audits |
|---|---|
| `INDECISION` | today's `choose()` stepping back onto the cell it just left, on a board whose walls and pickups did not change |
| `BACKSTEP` | today's `choose()` exploring leftward — walking against the belt toward cells it is about to deliver anyway |
| `PING-PONG` | the recorded run standing again where it already stood, belt unmoved, nothing collected |

`INDECISION` and `BACKSTEP` ask what **today's planner** would do on recorded
frames, so a fix has somewhere to show up. On `20260823T074036` `INDECISION`
went **3 → 0** with the fixes above.

`PING-PONG` audits what the recorded run *did*, which no fix changes
retroactively — so it is a hard violation only for footage produced by a
runner that already had the ledger (its log carries the `ledger` field), and a
printed count for older footage. The five it reports on `20260823T074036` are
the ~10 paws that run burned oscillating.

## PENDING (reason, plan, and why it is not done today)

**PENDING-A — `plan_tour` orders stops by position, not by cost.** On a board
with a column-0 orange reachable only through a pyramid and a free orange two
steps right, the tour takes the walled one first: ~4 paws + 200 shards for
+20E, against 2 paws for the same +20E. Roughly a 3× difference in energy per
action. Not fixed today because **no recorded run shows it happening** — it
was found on a synthetic board while writing a test, and the existing obstacle
pricing (a garra = 5 steps) is a calibration from real run data that should
not be re-tuned on a hypothetical. Plan: instrument the corpus for
`plan_tour` orders whose first leg crosses an obstacle, and decide with
evidence.

**PENDING-B — the explorer's cornered fallback contradicts its own comment.**
`movers or pool` falls back to a pool that still contains the leftward step,
and the comment above it says the opposite ("the left escape does not count as
an alternative, so a truly cornered explorer still breaks forward"). Left
(−40) outbids a forward garra (−83) whenever the rightward candidate has been
removed. After tying the perishable veto to reachable `tour_items`, the states
that remove the rightward candidate appear to be unreachable in practice — so
no honest failing test can be written for it today, and TDD forbids the fix
without one. The new `BACKSTEP` invariant will surface it the moment it
becomes reachable.

**PENDING-2 (carried, narrowed)** — Unify the erosion veto. Removing
`suspect_risk` took the suspect half out of all five dash rules; the five
`*_risk` sets are still computed inline with different steps-card policies.

**PENDING-3 (carried, one value settled)** — One economy constants block. The
steps card is **+5 paws / 200 shards**, measured; `pickup_type`'s docstring
already said so, `review-2026-08-22.md` said +4/160 and `auto_digiworld.py`
said "~3-5 (130-200)". The rest of the constants are still restated inline.

## Session 2 (afternoon): five live episodes, 320 actions

The first live runs under the paw receipt. Every defect below was found by
running the bot for 40-80 actions, replaying the recording through the
harness, and reading the frames the harness flagged. Numbers are from the
run logs, not estimates.

| ep | actions | taps refused | wait frames | s/action | energy/h |
|----|---------|--------------|-------------|----------|----------|
| 1  | 40      | 3 / 39 (7.7%)| 4           | 1.25     | (unreadable) |
| 2  | 60      | 6 / 59 (10%) | 4           | 1.19     | 38,895   |
| 3  | 60      | 2 / 57 (4%)  | 7           | 1.33     | 49,135   |
| 4  | 80      | 0 / 77       | 3           | 1.18     | 56,671   |
| 5  | 80      | 0 / 79       | 2           | 1.12     | 40,607   |

Energy per hour is dominated by what the board happens to hold, so it is not
a controlled measure; refused taps, wait frames and seconds per action are.

**FIXED-1 — the closing energy read lost to a pickup animation.** Run
20260823T142253 collected an orange on its last step; the icon was still
flying across the counter when the final screenshot was taken, so
`read_energy_counter` returned `None` and a run whose energy the loop had
read cleanly in 36 of 38 frames reported "Contador de energía ilegible".
`final_energy` now retries while the animation clears and, failing that,
falls back to the last reading the loop itself trusted. `energy_hud.end_source`
records which one was used.

**FIXED-2 — two goals traded the player between two cells for eight frames.**
Run 20260823T143257 n=45-52: from row 1 the orange at (0,3) won, from row 0
the dash-pair launch at (1,1) won, and the board never changed. Six paws for
zero progress. The explorer's own −30 reversal penalty never saw it because
the two goals live in different branches of `choose()`. The law is physical:
a charged step that collected nothing and did not scroll leaves the board
byte-identical, so walking back re-enters a state already judged. `choose()`
now takes `blocked_direction`, closes the cell we came from and asks again,
and keeps the original answer if the closed board has none.

**FIXED-3 — the veto was recomputed from an empty receipt.** Run
20260823T150408 n=70-72 walked back to (3,1) anyway, because a
wall-stabilizing WAIT sat between the step and the replan and cleared the
veto. The fact is about the board, not the frame: `next_blocked_direction`
now leaves a standing veto alone on any frame that brings no receipt.

**FIXED-4 — an immortal pyramid froze a run for 579 frames.** Run
20260823T145105 asked for 80 actions, executed 46, then repeated one frame
forever: the world model believed a pyramid at (0,2), merged it as an
obstacle every frame, the planner chose a garra at it every frame, and the
runner refused the garra every frame because raw vision saw an empty cell.
`Track.believed` returns `True` unconditionally for pyramids, so the track
could never die, and the skip path only cleared `phantom_obstacles`. Raw
pixels at the instant of the swing outrank a track built from earlier
frames: `WorldModel.refute(cell)` drops it, and the next frame that really
sees the pyramid starts a new track.

**FIXED-5 — no ceiling on frames that do nothing.** The run above never
reached `--steps`, so it had no way to end; every skip path is a local
"replan and try again" and nothing bounded how many could follow each other.
`MAX_IDLE_FRAMES = 25` ends the run with exit code 8 and a message naming the
run directory. This is a safety net, not the fix for any particular
livelock.

**FIXED-6 — the PING-PONG invariant called a paid detour waste.** Run
20260823T144136 n=12-16 walked two cells down for a claw and back up through
(3,0); the rule asked "did THIS cell hold an item" and the claw had been
collected one frame earlier. It now compares a pickup counter between the
two stands.

**NEW — the run log says what the run cost.** `efficiency_report` /
`format_efficiency` close every run with taps charged vs claimed, refused
taps, wait frames, seconds per action and energy per paw, and the same block
is written to the log as `efficiency`. Before this, a pathfinding change
could only be judged by watching the emulator.

### Open, with evidence

**PENDING-C — batching a second tap is close to free of value.** Across
episodes 1-3 (before the veto), a 1-tap frame lost 3 of 59 taps (5%), a
2-tap frame lost 4 of 13 (31%) and a 3-tap frame lost 2 of 3. A batch that
lands saves about 0.85 s; one that does not costs a re-plan and usually a
wait frame. At a 31% failure rate the two roughly cancel, and the failures
also mint phantom obstacles. Episodes 4 and 5 refused nothing at all, which
muddies the picture rather than settling it: the sample is 16 multi-tap
frames total. Not changed today because the honest measurement is an A/B
over a few hundred actions with `--batch-size 1`, which is the next thing to
run.
